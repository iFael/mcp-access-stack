# Update Control deployment preparation

Status: configuration and service templates only. No Cloudflare Worker, Tunnel, Access application, hostname, route, or secret is provisioned by this preparation.

## GitHub Actions deployment boundary

- Workflow: `.github/workflows/update-control-deploy.yml`.
- PRs run locked dependency installation, Worker check/dry-run, Worker tests, Orchestrator build/tests, and static/systemd template validation. The PR job has no GitHub Environment and reads no secrets or variables.
- Pull requests run validation without GitHub Environment access or secrets. Production deployment is available only through a manually dispatched workflow on `main`, with an explicit confirmation input and protected GitHub Environment `update-control-production`; merging any PR cannot deploy.
- Wrangler comes from `services/update-control-worker`'s locked workspace dependency (`wrangler` 4.135.0). The deploy command names only `services/update-control-worker/wrangler.jsonc`; it does not call Public release, `release.yml`, `edge-breakglass.yml`, or the Edge Worker.
- The deploy step fails before Wrangler if the Environment secret `UPDATE_CONTROL_CF_API_TOKEN`, variable `CLOUDFLARE_ACCOUNT_ID`, fixed HTTPS `UPDATE_CONTROL_OAUTH_REPROVISION_URL`, Access issuer, or Access audience is absent/invalid. The deploy token is mapped to Wrangler's `CLOUDFLARE_API_TOKEN` process environment without printing it. The non-secret Access configuration is injected as `MCP_UPDATE_CONTROL_OAUTH_REPROVISION_URL`, `MCP_UPDATE_CONTROL_OAUTH_REPROVISION_ACCESS_ISSUER`, and `MCP_UPDATE_CONTROL_OAUTH_REPROVISION_ACCESS_AUDIENCE`.
- The separate `.github/workflows/update-control-oauth-reprovision.yml` is manual-dispatch-only, main-only, explicitly confirmed, and uses the same protected Environment/concurrency lock. It changes only the Worker `MCP_OWNER_TOKEN` secret and calls the fixed Access-protected operation; it does not deploy Edge, invoke Public release, or change Cloudflare Access configuration.
- Configure the GitHub Environment with main-only deployment restrictions and required reviewers before placing its token. YAML references the Environment; it cannot create or prove its external reviewer/branch protection rules.

The source credential directory is root-owned mode `0700`; each source secret file is root-owned mode `0600`. systemd `LoadCredential` provides each service a read-only per-service credential file. Ledger/artifact state is under `/var/lib/mcp-access-stack-update-control` with mode `0700`, outside immutable code releases. The dedicated Orchestrator code root is `/opt/mcp-access-stack/update-control/current`, independent of the Edge runtime release path.

## Oracle services

- `mcp-v3-oracle-read-api.service` starts the Orchestrator read API on explicit `127.0.0.1:9381`, using the durable state directory above. It uses the credential-file input added to `start:read-api`; its bearer is not a process argument or environment literal.
- `mcp-v3-update-control-cloudflared.service` runs the outbound Cloudflare Tunnel connector with `--token-file` pointing to systemd's protected credential directory. It has no inbound listener and uses a separate DynamicUser from the API.
- Both units have bounded restart behavior and systemd hardening. Missing credentials or binaries fail closed; the units are versioned but are not installed, enabled, or started in this change.
- Do not create a firewall rule or bind the Oracle API to a public/interface address. Tunnel/Access hostname and service-auth policy require a later separately authorized provisioning step.

## OAuth recovery and rotation — controlled reprovisioning is canonical

The Durable Object namespace has one name (`update-control-auth-v1`) and one logical OAuth state unit. Its OAuth package stores `owner:credential-material:v1` (owner verifier hash, signing key, credential version), `owner:user-id:v1`, `owner:client-count`, `owner:client:<id>`, hashed authorization-code records `owner:code:<hash>`, hashed refresh-token records `owner:refresh:<hash>`, and revoked access-token metadata `owner:revoked:<jti>`. Access JWTs are stateless and signed with the persisted signing key; there is no separate session-record table. The wrapper identity is `update-control:owner-identity:v1`. No Orchestrator run ledger or update evidence lives in this Durable Object. Reprovisioning deletes the `owner:` namespace and that one identity key, preserves all other keys, and retains its own audit records under `update-control:oauth-reprovision:v1:`; deleting/recreating the entire Durable Object is not used.

Changing `MCP_OWNER_TOKEN` alone does not rotate persisted credential material. Before the first OAuth client is authorized, an operator uses the separate protected GitHub workflow to set the replacement Worker secret and invoke only `POST/GET https://<dedicated-access-host>/_operations/oauth/reprovision` through a Cloudflare Access service token. The Access-protected status preflight remains available when `MCP_OWNER_TOKEN` is absent, while normal MCP/OAuth/API requests fail closed; this lets the workflow inspect `not_executed` before installing the first owner token. Before persisting intent or deleting state, POST validates that the replacement OAuth configuration can be constructed. The Worker accepts only a UUID `operationId` and the fixed path on a dedicated HTTPS origin distinct from the public MCP origin. The path is not an MCP tool; it has no generic admin or storage operation. A manually configured Cloudflare Access application/policy must protect the dedicated host and permit only the GitHub Environment service token. The Worker also verifies the Access JWT's RS256 signature against the configured issuer's bounded JWKS, exact issuer, audience, expiration, and not-before claims; missing config, key-fetch failure, malformed token, or claim mismatch fails closed. Direct `workers.dev`/public MCP hosts do not match the configured operations origin.

The protected workflow requires a deliberate choice confirming invalidation, a stable UUID, and a replacement `MCP_OWNER_TOKEN` of at least 32 characters. It streams the secret through locked Wrangler stdin, calls the operation with the same UUID, and polls bounded batches. Durable status and audit events distinguish `not_executed`, `in_progress`, `completed`, and `outcome_unknown`; only operation metadata/event names/timestamps are recorded, never token material. If an operation is ambiguous, normal OAuth stays blocked. A future operator must inspect status and explicitly dispatch again with the same operation ID and same replacement token; no new ID or blind rollback/retry is allowed.

On completion, every OAuth client registration, authorization code, refresh token, revoked-token entry, owner verifier and signing key is invalidated. All old access JWTs fail signature verification; old refresh tokens and auth codes have no corresponding client/state. The next authorization uses only the new `MCP_OWNER_TOKEN`, and each client must register and explicitly authorize again. Old sessions/tokens are not preserved. Orchestrator run records/evidence and Edge state are not touched. Rolling back Worker code cannot silently revive old OAuth: persisted replacement credential material remains authoritative; changing the Worker secret back to the old value makes the Worker fail closed until a separately approved reprovision.

This mechanism is implemented and unit-tested but was not dispatched and has not run against Cloudflare. Before first real use, deploy the Worker code/operations URL through the separate protected deploy workflow, provision the Access app/service-auth policy and GitHub Environment values/secrets, then dispatch the OAuth workflow with a new UUID and explicit confirmation. Keep `UPDATE_CONTROL_OWNER_TOKEN_NEXT` until `completed`; then transfer the same value to the password manager and remove the temporary GitHub secret. No state should be edited manually in the Cloudflare dashboard.

## Provisioning sequence after authorization

1. Create/protect GitHub Environment `update-control-production`; restrict deployments to `main` and require review. Store the separate Worker-scoped Cloudflare API token as `UPDATE_CONTROL_CF_API_TOKEN` and account ID as `CLOUDFLARE_ACCOUNT_ID`.
2. Provision the Oracle tunnel and protected read API; create the Oracle-origin Cloudflare Access service token for `ORACLE_ACCESS_CLIENT_ID`/`ORACLE_ACCESS_CLIENT_SECRET` and the Worker/Oracle bearer `UPDATE_CONTROL_ORCHESTRATOR_TOKEN`. These are distinct from the OAuth-operations service token.
3. Create a dedicated hostname/route to the Update Control Worker for `/_operations/oauth/reprovision`, attach a Cloudflare Access application and service-auth policy, and create its service token. Store the URL as GitHub variable `UPDATE_CONTROL_OAUTH_REPROVISION_URL`, the service-token client ID as `UPDATE_CONTROL_OAUTH_ACCESS_CLIENT_ID`, and its secret as `UPDATE_CONTROL_OAUTH_ACCESS_CLIENT_SECRET`.
4. Put `UPDATE_CONTROL_OAUTH_REPROVISION_URL` in the protected GitHub Environment so the manual deploy workflow injects it as Worker var `MCP_UPDATE_CONTROL_OAUTH_REPROVISION_URL`. Keep the OAuth operations hostname distinct from the MCP hostname. No Oracle port is exposed.
5. Manually dispatch the independent Update Control deploy workflow on `main` with `DEPLOY_UPDATE_CONTROL` after runtime secrets/config and Access protection are ready. This step publishes only the Update Control Worker; it does not run in this branch/PR.
6. Before first real OAuth use, generate a new high-entropy owner token (at least 32 characters), save it in the password manager and temporarily as protected Environment secret `UPDATE_CONTROL_OWNER_TOKEN_NEXT`. Manually dispatch `Update Control OAuth controlled reprovision` on `main`, enter a UUID and select `REPROVISION_OAUTH_AND_INVALIDATE_ALL_SESSIONS`. Reuse the same UUID and token only when reconciling an ambiguous/interrupted operation.
7. After `completed`, remove the temporary GitHub secret; perform a safe OAuth reauthorization smoke with a synthetic client, then proceed to the already-approved plugin refresh/homologation gate. Do not edit Durable Object keys in the dashboard.

This branch only versions preparation/workflows. It creates no Cloudflare resource, sets no secret, dispatches no workflow, changes no OAuth state, and starts no service.
